# Lightdash Rules

Binding rules for the Lightdash BI and agentic-analytics integration in this repository.

## Ownership

1. **One generator, marker-owned blocks, regenerate-never-edit.**
   `scripts/lightdash_context_sync.py` owns every `meta:` block carrying the inline
   `# generated: lightdash_context_sync` marker and everything under
   `lightdash/knowledge/`. A `meta:` without the marker is a hand-authored decision:
   left alone and reported, never merged with. A schema file whose header names
   another generator (`# GENERATED by scripts/ontology_to_dbt.py`) is refused whole —
   one generator never edits another's file.
2. **One regeneration path.** `python3 scripts/use_case_sync.py --use-case <slug>
   --stage lightdash`. It runs after the ontology stages on purpose: the bridge
   projects `column-annotations.json`, so running it earlier projects the previous
   generation.
3. **After the bridge writes meta, re-run `dbt parse`** (`artifacts/refresh.sh`).
   Lightdash reads the manifest, not the YAML — meta the manifest does not carry does
   not exist for `lightdash compile` or `deploy`.

## Definitions

4. **Never write a metric** (analytics rule 42). The Lightdash CLI translates
   MetricFlow metrics from the manifest natively; a `meta.metrics` block restating one
   is a second source of truth. Metric classes the translator skips — cumulative,
   conversion, time-offset, cross-model — are served by the Wren metric views and named
   in `lightdash/knowledge/semantic-coverage.md`, never approximated as meta metrics.
5. **Joins are derived, never invented** (analytics rule 5). Every `meta.joins` entry
   comes from a dbt `relationships` test; `relationship:` cardinality only from
   `unique` tests, omitted where untested; `type: left` because MetricFlow joins
   dimension sources LEFT OUTER and an INNER join measurably dropped guest-checkout
   orders. `primary_key` only where exactly one column is unique+not_null tested.
6. **PII hiding comes from `column-annotations.json` and nowhere else** (analytics
   rule 17). `pii: direct` becomes `dimension.hidden: true` in every model that
   declares the column. Unhiding a column means changing the annotation and
   regenerating, not editing the meta.

## Gates

7. **`lightdash compile --skip-dbt-compile --skip-warehouse-catalog` is the no-server
   gate.** The verdict distinguishes what the bridge caused from what it observed:
   `fail` only when a failing explore carries bridge meta; a project whose columnless
   models cannot compile offline is `unready` — reported, counted, never red.
   No Node or no CLI means skip with the remedy named; unavailable is not failed.
8. **Pins move together.** The `external/lightdash` submodule SHA and the
   `@lightdash/cli` version (repo-local `.lightdash-cli/`, gitignored) are the same
   release. Upstream defects get a workaround in the bridge plus a ready-to-send patch
   under `external/patches/`, never fork-drift.

## Egress and credentials

9. **`lightdash deploy` and the preview commands ship the compiled project to an
   instance, and a connected instance runs SQL against the warehouse.** Deploying
   anywhere other than a locally-run instance is data egress: never without explicit,
   per-deploy user confirmation. Credentials (`LIGHTDASH_URL`, `LIGHTDASH_API_KEY`,
   `LIGHTDASH_PROJECT`) live in the environment only — no generator, config file, or
   MCP registration ever writes a token to disk.
