# Source Contract — Enhanza connector APIs

The standard [source-contract template](../../../../templates/source-contract.md) is one
file per source table. This project has nine connectors and roughly 170 raw tables, so the
contract is written once for the **connector class** — every connector lands the same way —
plus a per-connector table for what differs.

A new connector is not onboarded until its row here is filled in. See
[CONNECTORS.md](CONNECTORS.md) for the procedure.

---

## 1. Identity

| Item | Value |
|---|---|
| Source systems | Favrit, Fortnox, SevenTime, Tempo, Tripletex, Upsales, Visma eAccounting, Visma e-conomic, Xledger |
| Landed by | Enhanza ingestion jobs, one per connector API **[NEEDS INPUT: job names / orchestrator]** |
| Warehouse location | BigQuery, `<project>.<source>_api_<uid>.<table>` — one dataset per connector **per tenant** |
| Tenant resolution | the `uid` run var; there is no default, so a run without it fails rather than building against the wrong tenant |
| dbt `sources.yml` entry | [dbt_project/models/sources.yml](dbt_project/models/sources.yml), source named `<source>_api` |
| Owner of the pipeline | **[NEEDS INPUT]** |
| Owner of the source systems | the connector vendors; schema changes arrive unannounced |

The source name carries the `_api` suffix — `source('fortnox_api', 'invoices')`. Note that
[source-conventions.md](source-conventions.md) writes `source('fortnox', 'invoices')`; the
docs are wrong and the code is right.

## 2. Grain and keys

| Item | Value |
|---|---|
| Grain | one row per source-system record, per tenant |
| Primary key | source-native id column, unique **within a tenant dataset only** |
| Is the PK actually unique? | **[NEEDS INPUT]** — not verified by a test at the source layer |
| Cross-source key | `<Column>ERP = <Column>Id \|\| '-ds_<source>'`, generated by `add_erp_fields()` |
| Organization key | `ErpOrgId`, aliased per source in `global_configs('erp_columns_rename_and_cast_list')` |

The `-ds_<source>` suffix is what keeps ids from two connectors from colliding after the
union. It is applied to every column ending in `Id` except those in
`global_configs('id_erp_exceptions')`. **A connector added without a
`global_configs → erp_columns_rename_and_cast_list → dim_company` alias for its own
organization id column produces rows with a null `ErpOrgId`** — they survive every test and
vanish from every company-scoped query.

## 3. Freshness

| Item | Value |
|---|---|
| `loaded_at_field` | **not declared on any of the 17 sources** |
| `freshness:` blocks | **zero** |
| Actual load cadence | **[NEEDS INPUT]** per connector |
| Consumer's real need | app.enhanza.com expects data "as soon as the warehouse and dbt layers refresh" — not a testable SLA |
| Who is paged on a breach | **[NEEDS INPUT]** |

**This is the largest open gap in the use case.** Rule 14 requires `loaded_at_field` and
`freshness:` on every source feeding a scheduled mart; none of the nine connectors has
either, so `dbt source freshness` cannot run and a dead connector is indistinguishable from
a quiet one.

There is a partial substitute: the `latest_source_sync` view calls
`get_latest_source_timestamp()`, which reads BigQuery's `__TABLES__.last_modified_time`
across every enabled connector and feeds Cube's `refreshKey`. That answers "has anything
landed recently", not "is this source late", and it is a cache hint rather than an alert.

When declaring `loaded_at_field`, use a **warehouse load timestamp, not the source system's
`updated_at`** — a dead pipeline looks fresh forever if one old row was recently edited.

## 4. Mutability

| Item | Value |
|---|---|
| Are rows updated in place? | **[NEEDS INPUT]** — assumed yes for invoices, orders, and customers |
| Are rows hard-deleted? | **[NEEDS INPUT]** |
| History captured | none. The only snapshot in the project is `orders_scaffold_snapshot`, which belongs to the starter scaffold, not to any connector. |

If any connector overwrites values the business needs historically — invoice status,
customer tier, article price — that history is being destroyed today. A snapshot on the raw
source is the fix, and its `unique_key` and `strategy` can never be changed after the first
run, so it is worth deciding before the first tenant needs it.

## 6. Schema-change policy

Connector vendors change their APIs without notice, and the ingestion jobs land whatever
arrives. What that means per layer:

| Layer | Exposure |
|---|---|
| `<source>_bi_*_staging` | enumerates columns, so a new upstream column is ignored and a removed one fails loudly. This is the intended quarantine. |
| `<source>_erp_bi_<concept>` | must match every other source's adapter for the same concept. A column added to one adapter and not the others breaks the `UNION ALL` at compile time — which is the desired outcome. |
| `logic_bi_*` | the contracted layer. A breaking change here must fail the build, not the dashboard. |

## 7. Assumptions and what breaks

| Assumption | If wrong | Test |
|---|---|---|
| A connector's registry entry matches its models on disk | Silent under- or over-counting in every unified fact | `tests/test_enhanza_connector_registry.py` ✅ |
| Source-native ids are unique within a tenant dataset | Fan-out on every join through `<Column>ERP` | **none — [NEEDS INPUT]** |
| Every connector aliases its org id to `ErpOrgId` | Rows drop out of company-scoped queries with no error | **none — add a `not_null` on `ErpOrgId` per adapter** |
| Sources are loaded before the dbt run | Marts silently rebuild on stale data | **none — no `freshness:` declared** |
| Currency codes in the registry match what the connector actually reports | Mis-valued revenue across the whole unified layer | **none — [NEEDS INPUT]** |

The bottom three rows are the work this contract exists to schedule.
