# Sample data — and how to test a use-case with it

This directory holds generated, referentially-coherent sample data for the project's
**sources**, plus the wiring that lets `dbt` treat it as a tenant called `demo`. With it,
the part of the project that matters most — the unified ERP union contract — builds and
tests **locally, on DuckDB, with no warehouse and no credentials**.

Everything here is generated by `scripts/dbt_seed_generator.py`; regenerate with
`python3 scripts/use_case_sync.py --use-case enhanza-analytics`. Hand edits are lost.
This README is the one hand-written file.

## The sample use-case test

One command, from the repository root:

```bash
python3 scripts/dbt_sample_build.py
```

What it does, and what "pass" means:

```
seeded   3 source table(s): seventime_api__expenseitems, shopify_api__products, visma_eaccounting_api__articles
built    shopify_staging_demo.shopify_bi_dim_articles   12 rows
built    erp_bi_demo.erp_bi_dim_articles                36 rows
tests    2 run, 0 failing
union    SevenTime                                      12 rows
union    Shopify                                        12 rows
union    Visma e-Accounting                             12 rows
OK
```

That is `erp_bi_dim_articles` — the union the alignment checker once caught broken
(`isActive` vs `Active`) — built from three connectors' sample data, through each
connector's real adapter, into one relation with one conformed column list. The final
check is the one only a running database can make: **every enabled connector contributes
rows to the union**. 36 = 12 × 3, or the run fails.

Other concepts and connector mixes:

```bash
python3 scripts/dbt_sample_build.py --select erp_bi_dim_company \
    --connectors seventime,visma_eaccounting,fortnox

python3 scripts/dbt_sample_build.py --format json   # machine-facing summary
```

Prerequisites: `dbt-core` + `dbt-duckdb` (the repo's `.venv-dbt`, or set `DBT_BIN`),
`sqlglot`, and the `duckdb` Python package. Missing any of them, the runner exits `3`
(skip), never red — the same rule every optional toolchain in this repository follows.

## How it works

The project's SQL is BigQuery dialect; the local profile is DuckDB. Neither is changed.
dbt does everything it owns, and sqlglot owns the dialect boundary:

| Step | Tool | What happens |
|---|---|---|
| seed | `dbt seed -t demo` | loads these CSVs — dbt generates the inserts, dialect-free |
| compile | `dbt compile -t demo` | renders jinja, resolves `ref()`/`source()`, inlines ephemeral adapters |
| transpile | `sqlglot` | each compiled SELECT, BigQuery → DuckDB |
| execute | `duckdb` | materialises models in dependency order, runs the attached data tests |

The runner writes dbt artifacts to `target-sample/`, **never** `target/`: the canonical
manifest there is parsed with every connector enabled, and a compile with one tenant's
flags would silently replace it with a partial manifest — the exact corruption
`artifacts/refresh.sh` exists to prevent.

## How the seeds become sources

No edit to `sources.yml` anywhere. Three existing conventions line up:

1. Sources resolve `schema: <source>_api_{{ var('uid') }}` — so `uid: demo` means
   `fortnox_api_demo`.
2. `generate_schema_name()` on a non-production target emits `<custom>_<target.schema>` —
   so a seed configured `+schema: fortnox_api` on the `demo` target (whose
   `schema:` is `demo` in `profiles.yml`) lands at `fortnox_api_demo`.
3. Each seed's `alias` strips the `<source>__` filename prefix back to the table name.

`properties.yml` (generated) declares the alias and schema per seed, pins every column
`varchar` (staging casts explicitly — that is what staging is for), and gates
`enabled` on `target.name == 'demo'`, so a `dbt seed` against production cannot drop
sample tables into raw datasets.

## What is in the CSVs

- Sources are seeded, **not models**: `dbt build` derives the models, so the sample data
  exercises the real transformations instead of restating them.
- Which columns each CSV carries is read from the parsed SQL — every column the models
  reference against that source, in any select scope. Output lineage is not enough: a
  column read into a CTE and discarded by the final select is still selected by the
  compiled SQL, and its absence fails the build.
- Values come from `ontology/reference/*.csv` and nowhere else
  (the microsoft/Ontology-Playground convention, and rule 5). A column with no reference
  mapping gets a visibly fake placeholder (`somefield_value_3`) — never a plausible one.
- Deterministic: same manifest, byte-identical CSVs. A diff means the project changed.

## Scope — stated, not implied

Models whose inputs are JSON payloads (`json_extract_*`, lateral `unnest`) cannot run
from these seeds: a placeholder string is not a JSON document. The union concepts whose
full path is JSON-free, and therefore runnable here:

| Concept | JSON-free suppliers |
|---|---|
| `dim_articles` | seventime, visma_eaccounting, shopify |
| `dim_company` | seventime, visma_eaccounting, fortnox |
| `dim_cost_centers` | fortnox, xledger |
| `dim_customers` | seventime, shopify, fortnox |
| `dim_financial_years` | visma_economic, visma_eaccounting, fortnox, tripletex |
| `dim_projects` | visma_eaccounting, fortnox, xledger |

Everything else still gets its columns proven by the alignment checker's sqlglot pass and
its refs proven by `dbt parse` — what it does not get, locally, is an executed UNION.

## Troubleshooting

- **"no sample seeds"** → `python3 scripts/use_case_sync.py --use-case enhanza-analytics`
- **A model can't find a column** → the manifest is stale; run
  `./skill-packs/dbt-skills/use-cases/enhanza-analytics/artifacts/refresh.sh`, then
  regenerate the seeds (the sync command above).
- **`enhanza_sample.duckdb` or `target-sample/` in `git status`** → both are disposable
  run artifacts; delete freely. The runner rebuilds from scratch each time so a pass
  never means "leftover state".
