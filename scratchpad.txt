The Purpose of TOON in this Project
TOON (Token-Oriented Object Notation) is a serialization format designed for one primary purpose: to reduce the token count of structured data being passed into an LLM's context window. It achieves this by declaring the "header" or keys of a record list once, and then streaming the values, which is highly efficient for uniform, tabular data.

Why It's Not Used Everywhere: A Data-Driven Decision
The core principle for using TOON in this repository is: "Route a script through TOON only when it was measured to help."

The CLAUDE.md file contains a detailed table that shows the results of this measurement. For each script that can output JSON, the team compared the size of its plain text output against its TOON-serialized output.

Here's a summary of those findings:

| Command | text | TOON | | | |---|---|---|---|---| | dbt_column_lineage.py (40 edges) | 5445 | 3212 | −41% | routed | | connector_alignment_check.py (all connectors) | 1332 | 909 | −31% | routed | | dbt_column_memory.py --concept dim_articles | 4042 | 5292 | +30% | rejected | | use_case_sync.py --check | 587 | 854 | +45% | rejected | | dbt_manifest_to_graphify.py --dry-run | 271 | 633 | +136% | rejected |

The Winners: The scripts that benefit significantly from TOON, like dbt_column_lineage.py, are those whose output is one uniform record list. In this case, it's a list of ColumnEdge objects, where every object has the same keys. TOON excels here by not repeating the keys for every single edge.

The Losers: The scripts where TOON is worse are those whose output is already a concise summary of counts and statuses. Their JSON output is often more verbose than their text output, giving TOON nothing to effectively compress. As CLAUDE.md states: "A format cannot rescue output that is not a record list."

A Case Study in Measurement: dbt_column_memory.py
The documentation provides a fantastic "gotcha" example with dbt_column_memory.py --concept dim_articles. Initially, it measured as an 82% win for TOON. However, this was due to a bug where the --format json flag was ignoring the --concept filter and dumping the entire store. Once the bug was fixed and the JSON output correctly projected only the relevant concept, TOON was actually 30% worse than plain text. This highlights the project's commitment to accurate measurement over assumptions.

Automation and Enforcement
The project doesn't rely on developers to remember which scripts to pipe through TOON. It's automated:

The scripts/hooks/toon_graphify_pipe.py hook automatically rewrites calls to the "winning" scripts (like dbt_column_lineage.py) to pipe their output through the TOON serializer.
This ensures that TOON is used where it's beneficial and not used where it would be detrimental, without any manual effort.
In conclusion, yes, TOON really does help, but only in specific, measured scenarios. This repository's approach is a masterclass in engineering discipline: instead of applying a tool everywhere, it's applied only where data proves its value, and that application is automated to ensure consistency and prevent mistakes.

def _dedupe(edges: Iterable[ColumnEdge]) -> List[ColumnEdge]:
    seen: Set[ColumnEdge] = set()
    out: List[ColumnEdge] = []
    for edge in edges:
        if edge in seen:
            continue
        seen.add(edge)
        out.append(edge)
    return out
    # dict.fromkeys preserves insertion order for Python 3.7+. Since ColumnEdge is a
    # frozen dataclass, it is hashable and can be used as a dict key.
    return list(dict.fromkeys(edges))
